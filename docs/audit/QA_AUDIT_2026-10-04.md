## 3. Findings

### DATABASE

#### DB-01: The documented install fails on a stock MySQL 8 server

- **Severity:** High
- **Where:** `README.md` "First run" step 1; every migration that creates a trigger (starting with `001_notifications.sql`)
- **Reproduce:** Use a default MySQL 8.0 server (binary logging is on by default). Create the users with the exact README grants, then run `php bin/migrate.php`.
- **Expected vs actual:** Expected all migrations to apply. Actual: `Migration failed: SQLSTATE[HY000]: General error: 1419 You do not have the SUPER privilege and binary logging is enabled`. Migration 001 is left half-applied (tables created, no triggers, not recorded). [EXECUTED]
- **Why it matters:** A first deploy to any managed or standard MySQL host fails. An operator who "fixes" it by running as root defeats the privilege separation the design depends on.
- **Fix:** Document `SET PERSIST log_bin_trust_function_creators = 1` (or grant `SYSTEM_VARIABLES_ADMIN`/`SUPER` to the migrate account during migration only). Add a pre-flight check at the top of `bin/migrate.php` that reads `@@log_bin`, `@@log_bin_trust_function_creators` and `SHOW GRANTS` and stops with a clear message before running anything.
- **Effort:** S

#### DB-02: Migration 022 needs an undocumented privilege, can leave evidence unprotected, and is not re-runnable

- **Severity:** High
- **Where:** `database/migrations/022_remove_maintenance_and_roles.sql` lines 21–24 and 31–33; README grant list
- **Reproduce:** Use the README migrate grant (no `DELETE`) and run migrations 001–022.
- **Expected vs actual:** 022 runs `DROP TRIGGER photos_guard_update; DROP TRIGGER photos_guard_delete;` and then `DELETE FROM photos …`, which fails with `1142 DELETE command denied`. The DB is left with **no append-only guard on `photos`**, so damage-photo evidence can be updated or deleted. `users.role` has already been altered. A re-run then fails with `1360 Trigger does not exist` because there is no `IF EXISTS`. [EXECUTED; I confirmed only `status_logs_*` triggers remained on those two tables.] Separately, by design 022 drops the `status_logs` guards and deletes history rows, which goes against convention 1 (see section 5).
- **Why it matters:** An upgrade on a correctly locked-down server silently removes tamper protection from damage evidence, which is the basis for customer liability charges.
- **Fix:**
  1. Add `DELETE` to the documented migrate grant, or rewrite 022 so it does not need it.
  2. Use `DROP TRIGGER IF EXISTS`.
  3. Add `023_restore_photo_guards.sql` that recreates `photos_guard_update` and `photos_guard_delete` (drop if exists, then create) so half-upgraded installs heal.
  4. Make `bin/migrate.php` check the required privileges per migration before executing. MySQL DDL auto-commits, so a failure in the middle cannot be rolled back.
- **Effort:** S–M

#### DB-03: Soft-deleted master data blocks re-registration, and there is no restore

- **Severity:** Medium
- **Where:** `customer_identity_documents.uq_customer_identity_fingerprint`, `drivers.uq_drivers_license_fingerprint`, `vehicles.uq_vehicles_plate`; no `restore` method in `CustomerService`, `DriverService` or `VehicleService`; no vehicle soft-delete route at all
- **Reproduce:** Create a customer with passport `D12345678` → soft-delete → create a new customer with the same passport. Do the same for a driver's license number.
- **Expected vs actual:** Expected the record to be restorable, or the person re-registrable. Actual: `1062 Duplicate entry` (the UI says "already exists"), the deleted record cannot be found in any list, and no restore action exists. [EXECUTED]
- **Why it matters:** A returning customer or re-hired driver can never be entered again without a DBA. Convention 2 ("restoring works") is not met.
- **Fix:** Add `restore()` (admin only, audited via `status_logs`/`customer_notes`) for customers and drivers, plus a "Show deleted" filter. If re-registration should also be possible, scope uniqueness to live rows. For example:
  ```sql
  ALTER TABLE drivers
    ADD live_license_fp CHAR(64) CHARACTER SET ascii COLLATE ascii_bin
      GENERATED ALWAYS AS (IF(deleted_at IS NULL, license_number_fingerprint, NULL)) STORED,
    DROP INDEX uq_drivers_license_fingerprint,
    ADD UNIQUE KEY uq_drivers_live_license (live_license_fp);
  ```
  Restoring is preferable to re-creating because it keeps rental history linked.
- **Effort:** M

#### DB-04: Customer phone numbers are encrypted in one table but stored in plaintext in three others

- **Severity:** Medium
- **Where:** `notifications.recipient_phone` (also linked through `notifications.customer_id`), `rules_acceptances.phone`, `inbound_sms_events.sender_number` and `raw_payload`
- **Reproduce:** `SELECT recipient_phone, customer_id FROM notifications;` returns `+639025018869`-style values next to the customer ID. [EXECUTED; 12 distinct plaintext numbers]

#### BE-01: A vehicle can be double-booked on the hand-off day

- **Severity:** High
- **Module:** M5
- **Where:** `app/Services/BookingOverlapService.php:27`; `RentalService::create`
- **Reproduce:**
  - Rental A: `2026-12-08 → 2026-12-10`, return at 20:00.
  - Rental B, same vehicle: `2026-12-10 → 2026-12-12`, pickup at **08:00**.
- **Expected vs actual:** Expected B to be refused, because the car is still out until 20:00. Actual: B was created (`OK:65591`). [EXECUTED]
- **Why it matters:** This is a real double-booking. The second customer arrives 12 hours before the car is back. Overlap is checked on whole Manila dates only, and the stored `scheduled_pickup_at/return_at` times are ignored.
- **Fix:** Check conflicts on the scheduled datetimes, with a configurable turnaround buffer (cleaning or inspection):
  ```sql
  … AND scheduled_pickup_at < :req_return + INTERVAL :buffer MINUTE
    AND scheduled_return_at + INTERVAL :buffer MINUTE > :req_pickup
  ```
  Keep the date rule for billing only. Add an index on `(vehicle_id, status, scheduled_pickup_at, scheduled_return_at)`.
- **Effort:** S–M

#### BE-02: Concurrent driver assignment double-books a driver

- **Severity:** High
- **Module:** M6
- **Where:** `app/Services/ChauffeurService.php:21-50` (`assignDriver`)
- **Reproduce:** Use two chauffeur agreements on different vehicles for the same dates. Assign the same driver to both at the same moment (`scripts/t_race_driver.php`).
- **Expected vs actual:** Expected one success and one "overlapping assignment" refusal. Actual: **both succeed**, 3 runs out of 3, including runs with no artificial lock. [EXECUTED]
- **Cause:** The transaction's first statement is a non-locking `find()`. Under REPEATABLE READ this fixes the snapshot *before* `lockDriver()` waits. The overlap check that runs after the lock is a plain `SELECT`, so it reads the stale snapshot and never sees the other transaction's committed assignment. The vehicle path does not have this problem because its first statement is a locking read. That is confirmed: 12 parallel bookings produced exactly 1 success. `transition('confirm')` uses the same snapshot-before-lock pattern [STATIC].
- **Impact:** The later `confirm` check catches the overlap, but then **both** paid bookings are refused until staff reassign a driver. [EXECUTED]
- **Fix:** In `BookingOverlapService::conflicts`, make the query a locking read (`… LIMIT 1 FOR SHARE`). A locking read sees the latest committed rows whatever the snapshot is. Also lock the driver row before any consistent read in `assignDriver`/`transition`, and run the existing race script in CI.
- **Effort:** S

#### BE-03: Any visitor can permanently lock out any staff account, including the only admin

- **Severity:** High
- **Module:** M1
- **Where:** `app/Services/AuthService.php:46-55`; `StaffUserRepository::recordFailedLogin`; `AUTH_MAX_FAILED_LOGINS`
- **Reproduce:** Send 5 POSTs to `/staff/login` with a known staff email and a wrong password.
- **Expected vs actual:** Expected a temporary slowdown. Actual: the account is locked indefinitely. The correct password then returns 401. With one active admin, `unlocked_admins=0`: nobody can unlock anyone, and recovery needs a manual DB `UPDATE`. [EXECUTED]
- **Why it matters:** Staff emails are easy to guess (`admin@…`). One attacker request per staff member stops the business.
- **Fix:**
  - Replace the permanent lock with a time-based lock (`locked_until = now + 15 min × 2^n`, capped).
  - Throttle per IP and account pair.
  - Optionally require step-up (CAPTCHA) after 3 failures.
  - Never hard-lock the last active `system_admin`.
  - Add `bin/unlock-user.php` as a break-glass tool.
- **Effort:** S–M
