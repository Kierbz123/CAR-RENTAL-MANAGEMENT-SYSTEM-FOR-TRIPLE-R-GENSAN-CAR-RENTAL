# Step 0 — Greenfield reconnaissance

Recorded against the greenfield checkout before the next feature. The initial repository contained only its README; Feature E is the first application module. This record is therefore an inventory of the new codebase and the confirmed product plan, not evidence about a pre-existing rental application. Feature E's migration already exists; this appendix is retrospective and does not claim Step 0 preceded it.

| # | Master prompt question | Finding and decision |
|---|---|---|
| 1 | Driver account location and identifying columns | No driver table or driver login existed in the initial repository. The approved system model depicts `drivers` separately from staff `users` and says drivers have their own login. Implement a separate `drivers` table and driver identity for Feature D; do not treat staff accounts as drivers. Exact driver columns will be specified with the GPS/driver feature. |
| 2 | Existing SMS integration | None existed. Feature E adds the `notifications` queue and one provider adapter interface for Semaphore and PhilSMS. Provider credentials and registered sender names are environment settings; callbacks require the documented signed gateway contract. |
| 3 | Existing GCash verification | None existed. Feature B will use manual reconciliation against GCash transaction history, with `fleet_manager` and `system_admin` staff roles per the approved plan. Payment and booking statuses must follow the canonical master prompt state machine. Proof files belong in private storage. |
| 4 | Existing rules and acceptance tracking | None existed. Feature C must introduce immutable `rules_versions` and append-only `rules_acceptances`; acceptance must be scoped by consent kind and evidenced as specified by the master prompt. |
| 5 | Existing price calculation and rental-day component | Neither existed in the initial repository. This is a greenfield exception to the master prompt's instruction to reuse existing pricing. The current plan says not to rebuild pricing, but there is no implementation to reuse; pricing and inclusive date/day semantics need an explicit product rule before Feature A can be finalized. Store monetary values as `DECIMAL`, never floating point. |
| 6 | Existing booking, hold, availability, and vehicle blocking | None existed. Feature A must implement these. The canonical booking/hold states and overlap protection are in the master prompt; use InnoDB transactions and conditional writes, with `REPEATABLE READ` for availability/booking creation. |
| 7 | MySQL version and isolation | No database server or existing application isolation setting was available in this environment. The target is MySQL 8.0+ / InnoDB, configured to UTC by the PDO connection. The server's default isolation is not runtime-verified; booking creation must explicitly ensure `REPEATABLE READ` and record/restore any connection-level change. |
| 8 | Existing scheduler | None in the initial repository. Feature E documents a one-minute cron and Windows Task Scheduler invocation. Later expiry, retention, and archival jobs must be added as CLI entry points and scheduled explicitly. |
| 9 | Existing dashboard/auth conventions | None existed. Feature E introduces the PHP front controller/router, PDO repositories, session auth, CSRF helper, and `system_admin` / `fleet_manager` staff roles. Extend these patterns; drivers remain a separate identity as recorded above. |
| 10 | Existing filesystem and uploads | No existing upload storage. The public document root is `public/`; private runtime files belong in the project `storage/` directory outside it. Feature A/B uploads must validate MIME and extension, reject HEIC, strip EXIF where applicable, enforce size limits, and be served only through staff-authorized code. |

## Constraints carried forward

- The master prompt puts shared Magic-Link infrastructure before booking/payment, while its required `booking_access_tokens` rows need `booking_id` and `expires_at = min(48h, bookings.hold_expires_at)`. This greenfield repository has no `bookings` table. The persistence/API boundary must be resolved before implementing that feature; no booking-independent token schema is assumed here.
- Existing rental pricing, vehicle availability, user, rules, payment, and driver implementations cannot be reused because this is a greenfield project. Where the plan explicitly says to preserve existing behavior, there is no legacy behavior to preserve; product rules still need to match the canonical master prompt or be clarified where it assumes an existing component.
- PHP and MySQL executables are unavailable in the development environment, so database version/isolation and runtime behavior remain to be verified locally.
